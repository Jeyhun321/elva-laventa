# BUG_PROCESS — жизненный цикл бага Elva LaVenta

Официальная модель управления багами проекта. Работает вместе с
**[BUGS.md](BUGS.md)** (главный QA-документ и постоянный Regression Suite).

## Роли

- **Developer** — реализует исправление (в проекте: Claude Code как primary engineer;
  Codex как специалист/резерв).
- **QA** — проводит регрессию (в проекте: владелец на реальных устройствах/аккаунтах;
  AI-инженер готовит чек-листы и выполняет проверки, доступные из окружения: build,
  статический анализ, git-проверки).
- **Owner (владелец)** — принимает решение о деплое/релизе и подтверждает пострелизную
  проверку на проде.

## Официальные правила проекта

1. **До Release 1.0 статус `CLOSED` не используется.** Максимум — `POST-RELEASE VERIFIED`
   → `ARCHIVED`.
2. **Ни один подтверждённый баг не удаляется** — только смена статуса и дополнение истории.
3. **Каждый исправленный баг навсегда входит в Regression Suite** (`Regression Checklist`
   в BUGS.md).
4. **Новый баг обязан появиться в BUGS.md со статусом `NEW`/`CONFIRMED` ДО начала
   исправления.**

---

## Модель жизненного цикла

```
NEW
  ↓
CONFIRMED
  ↓
IN PROGRESS
  ↓
FIXED
  ↓
READY FOR QA
  ↓
REGRESSION PASSED
  ↓
READY FOR RELEASE
  ↓
POST-RELEASE VERIFIED
  ↓
ARCHIVED
```

Дополнительные (боковые) статусы:
- **REOPENED** — баг снова проявился после `REGRESSION PASSED`/`POST-RELEASE VERIFIED`;
  возвращает баг на линию `CONFIRMED → IN PROGRESS`.
- **BLOCKED** — переход невозможен из-за внешней зависимости (например, ручное
  применение SQL владельцем); указывается причина в `Notes`.

## Статусы: кто переводит, когда, условия перехода, какие документы обновляются

### 1. NEW
- **Что значит:** баг зафиксирован, но ещё не воспроизведён/не подтверждён.
- **Кто переводит:** любой, кто нашёл (Developer / QA / Owner).
- **Когда используется:** сразу при обнаружении. Запись создаётся **до** любой правки кода
  (правило 4).
- **Условие перехода → CONFIRMED:** баг воспроизведён или root cause достоверно определён.
- **Документы:** создать запись в `BUGS.md` по шаблону (минимум: Title, Module, Platform,
  Description, Steps to Reproduce, Expected/Actual). При необходимости — `docs/TODO.md`.

### 2. CONFIRMED
- **Что значит:** баг подтверждён (воспроизведён или root-caused), готов к работе.
- **Кто переводит:** Developer или QA.
- **Когда:** после успешного воспроизведения/анализа.
- **Условие перехода → IN PROGRESS:** взят в работу разработчиком.
- **Документы:** `BUGS.md` (уточнить `Root Cause`, `Priority`, `Severity`); при
  планировании — `docs/TODO.md`.

### 3. IN PROGRESS
- **Что значит:** идёт исправление.
- **Кто переводит:** Developer.
- **Когда:** начата правка кода.
- **Условие перехода → FIXED:** правка завершена, локальные проверки (build/lint/тесты,
  если есть) пройдены; изменения сфокусированы.
- **Документы:** `BUGS.md` (`Developer`, черновик `Fix Summary`); при частичном/блокирующем
  состоянии — пометить `BLOCKED` с причиной.

### 4. FIXED
- **Что значит:** исправление реализовано в коде (в рабочем дереве или коммите), но ещё не
  прошло независимую регрессию в проверяемой среде.
- **Кто переводит:** Developer.
- **Когда:** правка готова; выполнены доступные автоматические проверки (`vite build` и т.п.).
- **Условие перехода → READY FOR QA:** изменения попали в среду, где QA может их проверить
  (обычно после деплоя или на предпросмотре).
- **Документы:** `BUGS.md` (финальный `Fix Summary`, заполнить `Regression Checklist`),
  `docs/HANDOFF.md` (текущее состояние), `docs/DAILY.md` (по факту работы),
  `docs/FEATURES.md`/`docs/DECISIONS.md` — если применимо.

### 5. READY FOR QA
- **Что значит:** исправление доступно для проверки QA.
- **Кто переводит:** Developer/Owner (после того как изменения оказались в проверяемой среде).
- **Когда:** сразу после деплоя фикса или подготовки предпросмотра.
- **Условие перехода → REGRESSION PASSED (Fix Verification):** QA прогнал `Regression
  Checklist` **только самого исправленного бага** (сам сценарий) на mobile и desktop — всё
  зелёное. Полная Regression Suite и чек-листы соседних багов на этом шаге **НЕ прогоняются**
  (новая политика: полный прогон — только перед релизом / крупными обновлениями / после
  значительных изменений архитектуры).
- **Документы:** `BUGS.md` (`QA`, старт записей в `Regression History`).

### 6. REGRESSION PASSED
- **Что значит:** исправление подтверждено Fix Verification (проверен сам исправленный
  сценарий). Полная регрессия здесь не требуется.
- **Кто переводит:** QA.
- **Когда:** после успешной Fix Verification исправленного бага.
- **Условие перехода → READY FOR RELEASE:** баг включён в состав ближайшего релиза и
  прошёл **полную** релизную регрессию вместе со всем Suite (см. триггеры в BUGS.md).
- **Документы:** `BUGS.md` (`Regression History` с датой и результатом).

### 7. READY FOR RELEASE
- **Что значит:** фикс проверен и включён в релиз-кандидат.
- **Кто переводит:** Owner (или Developer по согласованию).
- **Когда:** при формировании релиза, после релизной регрессии всего `BUGS.md`.
- **Условие перехода → POST-RELEASE VERIFIED:** релиз задеплоен и фикс подтверждён на
  проде.
- **Документы:** `docs/HISTORY.md` (веха релиза), `BUGS.md` (`Release`).

### 8. POST-RELEASE VERIFIED
- **Что значит:** фикс подтверждён в боевой среде после релиза.
- **Кто переводит:** QA/Owner.
- **Когда:** сразу после деплоя релиза, пострелизная регрессия на проде (mobile + desktop).
- **Условие перехода → ARCHIVED:** пройдено достаточно времени/циклов без регрессии; баг
  переводится в архив (но остаётся в Regression Suite).
- **Документы:** `BUGS.md` (`Regression History`), при необходимости `docs/HISTORY.md`.

### 9. ARCHIVED
- **Что значит:** баг закрыт по процессу (без формального `CLOSED` до Release 1.0),
  подтверждён на проде, остаётся в постоянном Regression Suite.
- **Кто переводит:** Owner.
- **Когда:** после устойчивого подтверждения на проде.
- **Условие «возврата» → REOPENED:** повторное проявление.
- **Документы:** `BUGS.md` (статус `ARCHIVED`, запись сохраняется навсегда).

### REOPENED (боковой)
- **Что значит:** ранее закрытый по регрессии баг снова проявился.
- **Кто переводит:** любой, кто обнаружил повтор.
- **Когда:** при регрессии на daily/release/post-release прогоне.
- **Условие перехода:** возвращается на `CONFIRMED → IN PROGRESS`.
- **Документы:** `BUGS.md` (`Regression History` с фактом повтора и датой), `docs/TODO.md`.

### BLOCKED (боковой)
- **Что значит:** переход невозможен из-за внешней зависимости (ручное действие владельца,
  доступ, инфраструктура).
- **Кто переводит:** Developer/QA.
- **Документы:** `BUGS.md` (`Status`/`Notes` с причиной блокировки).

## Связь со стратегией регрессии

**Regression Strategy** (Fix Verification после фикса; полная Suite только по триггерам;
пострелизная проверка; опциональный daily smoke; использование BUGS.md как чек-листа)
описана в **[BUGS.md](BUGS.md) → раздел «Regression Strategy»**. Здесь фиксируется, что
именно требуется на каждом переходе:

- `READY FOR QA → REGRESSION PASSED` — **Fix Verification**: проверяется **только сам
  исправленный сценарий** (чек-лист этого бага). Полная Suite **НЕ** запускается.
- `REGRESSION PASSED → READY FOR RELEASE` — **полная Regression Suite** всего `BUGS.md`,
  и только по триггерам: перед релизом / перед крупными обновлениями / после значительных
  изменений архитектуры.
- `READY FOR RELEASE → POST-RELEASE VERIFIED` — **Post-release проверка** на проде.
- Ежедневный smoke — опционален, вне переходов (может породить `REOPENED`).

## Анти-выдумывание (жёстко)

Никогда не выдумывать результаты регрессии, даты, build/test-результаты, деплои, SHA. Если
проверка не проводилась — `Regression History` = `NOT VERIFIED`. Неизвестное поле —
`UNKNOWN`. Соответствует правилам `CLAUDE.md`/`AGENTS.md`/`AI_WORKFLOW.md`.
