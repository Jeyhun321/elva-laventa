## [D-006] Admin → Storefront синхронизация через Supabase Realtime + ordering-guard
- **Дата:** 2026-08-15
- **Причина:** после правок в admin-панели открытый пользовательский сайт показывал старые данные до ручного refresh.
- **Рассматривались варианты:** (A) периодический polling каталога; (B) full-page reload по событию/таймеру; (C) Supabase Realtime (`postgres_changes`) → тихая ревалидация состояния.
- **Почему выбран этот вариант:** (C) — admin пишет напрямую в таблицы `products`/`categories` Supabase, поэтому Realtime на этих таблицах покрывает все editable-поля без параллельной системы данных. Reload запрещён требованием. Один канал в `CatalogContext`, debounce 300ms, cleanup при размонтировании; ревалидация тихая (без подъёма `loading` → без мигания). Гонку «свежие данные ↔ поздний ответ» закрывает монотонный `dataSeq` (последний запрос побеждает; initial load, visibility-revalidate и realtime-revalidate используют один guard).
- **Последствия:** таблицы `products` и `categories` должны быть в publication `supabase_realtime` — идемпотентный `supabase/realtime-catalog.sql` запускает владелец (без него подписка успешна, но событий нет — деградация до visibility-revalidate). У товаров нет localStorage-кэша (state в памяти + локальный файл-fallback), поэтому stale-cache перезаписи нет. Не ломать: единый `dataSeq`, единственный канал, cleanup (иначе утечки/дубли листенеров).

## [D-005] Favorites/cart без localStorage + session-token и request-version
- **Дата:** 2026-08-01
- **Причина:** гонки при быстрой смене аккаунтов (A→B→A): устаревший async SELECT/DELETE приходил позже нового и перезаписывал state старым снимком; orphan-id давал ложный бейдж.
- **Рассматривались варианты:** (A) сверять только `user.id`; (B) кэш в localStorage + merge; (C) session-token на каждую активацию аккаунта + monotonic request-version, свежий SELECT после каждой мутации, без localStorage-кэша для вошедшего.
- **Почему выбран этот вариант:** только (C) исключает применение устаревших ответов и перенос чужих данных между аккаунтами; localStorage как источник/цель для вошедшего убран полностью.
- **Последствия:** источник истины — Supabase по `user.id`. Нельзя возвращать localStorage-кэш для вошедшего. Бейджи считают только реально существующие в каталоге товары.

## [D-004] Заказ доступен любому вошедшему, а не только Google
- **Дата:** 2026-08-01
- **Причина:** email-регистрация добавлена, но заказ не проходил для не-Google.
- **Рассматривались варианты:** (A) правка только фронта; (B) снять проверку в БД-функции `place_order`; (C) фронт + отдельная безопасная SQL-правка.
- **Почему выбран этот вариант:** реальная блокировка была в SQL-функции (`provider='google'` → `GOOGLE_AUTH_REQUIRED`), а не во фронте. Создан `supabase/fix-order-any-auth.sql` — копия свежей версии минус только Google-блок; `auth.uid() is null → AUTH_REQUIRED` сохранён.
- **Последствия:** серверная цена, размеры, Telegram, очистка корзины и grants не тронуты. Применяет владелец вручную (нет production-доступа из окружения).

## [D-003] Галерея вариантов — по папке изображений, не по коду товара
- **Дата:** 2026-07-31
- **Причина:** оранжевое платье показывало бежевые фото — галерея определялась по общему коду товара.
- **Рассматривались варианты:** (A) ключ по коду товара; (B) ключ по папке изображений конкретного цвета.
- **Почему выбран этот вариант:** у вариантов один код, но разные наборы фото; папка изображения однозначно идентифицирует цвет.
- **Последствия:** нельзя возвращать определение галереи по коду товара.

## [D-002] Цветовые варианты: один код = один товар с несколькими цветами
- **Дата:** 2026-07-31
- **Причина:** нужно продавать один артикул в нескольких цветах с раздельными фото/ценой/размерами/наличием.
- **Рассматривались варианты:** (A) отдельный товар на каждый цвет; (B) один товар + строки-варианты по цвету.
- **Почему выбран этот вариант:** (B) — уникальность «код + цвет», колонки `color_name/color_hex/is_default_color/in_stock`, триггер держит один основной цвет; каталог схлопывает группу в одну карточку.
- **Последствия:** миграция `supabase/product-variants.sql` применена, есть блок отката. Не ломать уникальность «код+цвет» и триггер основного цвета.

## [D-001] Гостевая корзина отключена — вход обязателен
- **Дата:** 2026-07-31
- **Причина:** решение переигрывалось: сначала гостю разрешили корзину/избранное ради конверсии, затем владелец попросил вернуть обязательный вход.
- **Рассматривались варианты:** (A) гостевая корзина ради конверсии; (B) обязательный вход через единую точку проверки.
- **Почему выбран этот вариант:** владелец выбрал (B); проверка вынесена в начало `addToCart`/`toggleFavorite`, единый диалог `ShopAuthGate`.
- **Последствия:** **флаг спорный, менять только с подтверждения владельца.** Гостевой перенос корзины удалён (плодил фантомные строки).
